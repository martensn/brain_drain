**[2026-08-11, later same day] Reweighting redesign implemented, debugged, and verified — `survey::rake()` abandoned mid-implementation for a hand-rolled `manual_ipf()`.** The `rake()`/`postStratify()` route from the plan above hit a real, non-obvious limitation in the `survey` package, not a data problem:
- `rake()` calls `postStratify(..., partial=FALSE)` internally with no override (confirmed by printing `rake()`'s own source) — fails outright ("Strata in sample absent from population") whenever any sample stratum has zero matching population cell, which happens immediately with two separate margins this sparse.
- A hand-written `rake_partial()` (same algorithm, `partial=TRUE`) got past that error but hit a deeper one: even after restricting both margins to exactly the cells with real bidirectional sample coverage, `postStratify(partial=TRUE)` itself produces `NA` weights for thousands of rows whose stratum demonstrably *does* exist in the population table with a sane `Freq` (confirmed by hand-checking specific NA rows against `margin_demo` directly) — something inside `postStratify`'s own mechanism breaks when many population cells are simultaneously thin/absent, not a bug in this code's filtering.
- `survey::calibrate()` (tried next, since it's documented to support bounded weights) turned out to build one combined model matrix across all margins rather than doing separate sequential raking — a fundamentally different fit than what was needed, abandoned as out of scope.
- **Final mechanism**: `manual_ipf()`, a ~30-line hand-rolled iterative proportional fitting loop using plain `data.table` merges — alternates over the two margins, and (this is the actual fix, confirmed by testing) clamps each per-cell ratio to `[0.05, 20]` on **every iteration**, not just as a final post-hoc clip. The earlier `Inf`/`NA` blowups were traced to an unbounded ratio, not a matching problem — bounding it inside the loop fixes both the numerical instability and, indirectly, the South Dakota thin-cell issue (see below). Caught one silent-corruption risk before running on real data: `data.table::merge()` defaults to `sort=TRUE` and does **not** preserve row order, which would have silently misaligned every returned weight with the wrong row — fixed with an explicit `.rowid` tracked through every merge and restored before every comparison/return (verified with a deliberately-scrambled-row-order toy test).

RAC2P's actual codebook for the 2018-2022 5-year ACS (confirmed via `tidycensus::pums_variables`) is 2-digit (`"01"`=White, `"02"`=Black, `03`-`37`=American Indian/Alaska Native, `38`-`66`=Asian/Pacific Islander, `67`-`68`=Other/Two-or-more) — `acs_reweight.R`'s race-recode (from `Code/Old/06_census.R`, archived) assumed 4-digit codes (`"1000"`/`"3000"`/etc.), presumably written for an older/different PUMS vintage. Fixed by comparing as integers, restricting to MIGSP ≤ 56 (valid US state/DC range; Puerto Rico=072 and foreign-country codes 100+ fall back to current state, same treatment as a non-mover).
  - `Code/acs_pull.R` now checkpoints the raw pull separately (`Data/intermediate/pums_raw_pull.rds`) from the derived columns specifically so a future fix to this derivation logic doesn't require re-hitting the Census API (51 states x 80 replicate weights, real wall-clock cost).
