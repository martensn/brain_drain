**[2026-08-11, later same day] Reweighting redesign implemented, debugged, and verified — `survey::rake()` abandoned mid-implementation for a hand-rolled `manual_ipf()`.** The `rake()`/`postStratify()` route from the plan above hit a real, non-obvious limitation in the `survey` package, not a data problem:
- `rake()` calls `postStratify(..., partial=FALSE)` internally with no override (confirmed by printing `rake()`'s own source) — fails outright ("Strata in sample absent from population") whenever any sample stratum has zero matching population cell, which happens immediately with two separate margins this sparse.
- A hand-written `rake_partial()` (same algorithm, `partial=TRUE`) got past that error but hit a deeper one: even after restricting both margins to exactly the cells with real bidirectional sample coverage, `postStratify(partial=TRUE)` itself produces `NA` weights for thousands of rows whose stratum demonstrably *does* exist in the population table with a sane `Freq` (confirmed by hand-checking specific NA rows against `margin_demo` directly) — something inside `postStratify`'s own mechanism breaks when many population cells are simultaneously thin/absent, not a bug in this code's filtering.
- `survey::calibrate()` (tried next, since it's documented to support bounded weights) turned out to build one combined model matrix across all margins rather than doing separate sequential raking — a fundamentally different fit than what was needed, abandoned as out of scope.
- **Final mechanism**: `manual_ipf()`, a ~30-line hand-rolled iterative proportional fitting loop using plain `data.table` merges — alternates over the two margins, and (this is the actual fix, confirmed by testing) clamps each per-cell ratio to `[0.05, 20]` on **every iteration**, not just as a final post-hoc clip. The earlier `Inf`/`NA` blowups were traced to an unbounded ratio, not a matching problem — bounding it inside the loop fixes both the numerical instability and, indirectly, the South Dakota thin-cell issue (see below). Caught one silent-corruption risk before running on real data: `data.table::merge()` defaults to `sort=TRUE` and does **not** preserve row order, which would have silently misaligned every returned weight with the wrong row — fixed with an explicit `.rowid` tracked through every merge and restored before every comparison/return (verified with a deliberately-scrambled-row-order toy test).

## Decisions
- Column 2 ("actual sample") = `06_finalize_data.Rmd`'s broad `regression` table, not the tighter `regression_cbsa_10`/`state_10`
- `table.express`, once attached earlier in a session, masks `select()`/`mutate()` for data.tables via S3 dispatch — hand data.tables off to `as_tibble()` before plain dplyr chains. Found and fixed two more live instances this session (`05_merge.Rmd`'s `hs_zip`, which feeds `dist`, a hard filter in `06_finalize_data.Rmd`; and `06_finalize_data.Rmd`'s own `inst_group` merge) beyond the original `02_col_chars.Rmd`/`county_fips` case — same bug class, same `as_tibble()` fix.
- Column 1 structurally can't use HS-anchored birth-year imputation (`birth1 = hs_end - 18`, `04_li_ed_pos.Rmd` line 245) — only the cruder `birth2 = col_start - 18`, which assumes immediate HS-to-college enrollment. This systematically undercounts non-traditional-timing students (gap year, delayed enrollment, career-changers) relative to Column 2, and fully explains the superset gap (134,195 of Column 2's 3,092,892 users, 86.4% directly attributable, concentrated among "Non-Traditional" students) — worth a sentence in the memo, not something to fix (fixing it would require HS data, defeating Column 1's purpose).
- Column 1's population (50.45M pre-filter) is ~10x larger than initially assumed, since dropping the HS join removes the pipeline's main narrowing step — full pipeline re-runs from `01d` onward take ~6 hrs at Column 2's scale (skip `01a`/`01b`/`01c`, unaffected by Step 0); Column 1's build is far more expensive still (Section 2's position-matching alone: chunked `user_id %% 50` processing, ~35 chunks/9hrs, survived a mid-run machine reboot via per-chunk checkpointing)
- Remember to re-run `Code/scripts/convert_rmd_to_r.R` after editing a root `.Rmd` — `run_pipeline.R` executes the converted copies, not the `.Rmd`s
- `column1_population.rds` DOES carry `col_state`/`birth` natively (set during Section 2's position-matching/birth-year-waterfall step, `column1_merge[, col_state := state_abbr]`) — an earlier planning pass wrongly assumed Column 1 had no state-level geography at all and would need a fresh `colleges.rds` join to recover it. Verify against the live file's `names()` before trusting either claim if this comes up again.
- New Step 2 code (`memo1_covariates.R`/`acs_pull.R`/`reweight_column2.R`) uses `merge()` for every join, not data.table's `X[Y, on=]` bracket-chaining — confirmed empirically (small standalone test) that `X[Y, on=]` with no `j` DOES pull in both tables' columns, same as `merge()`, so this was extra caution rather than a necessary workaround; no bug resulted either way. `memo1_column1_construct.R`'s Section 1 code is the one exception, mirroring `01d_col_hs_construct.R`'s bracket-chain pattern verbatim (object substitution only) — also confirmed correct once actually run.
- Census region labels: use `Code/demographics.R`'s own `state_region_crosswalk` (Northeast/Midwest/South/West, Census-Bureau-consistent) everywhere geography is compared across the LI and ACS sides — NOT base R's `state.region`, which uses different category labels (e.g. "North Central" instead of "Midwest") and would silently break comparability with ACS's own region derivation.
- **`Code/acs_pull.R`'s R-4.6.0 first real run (2026-08-10) caught two genuine bugs inherited from `acs_reweight.R`**, both invisible to static code review and only caught by actually running against live PUMS data (same lesson as [[brain-drain-pipeline-verification]]):
  1. RAC2P's actual codebook for the 2018-2022 5-year ACS (confirmed via `tidycensus::pums_variables`) is 2-digit (`"01"`=White, `"02"`=Black, `03`-`37`=American Indian/Alaska Native, `38`-`66`=Asian/Pacific Islander, `67`-`68`=Other/Two-or-more) — `acs_reweight.R`'s race-recode (from `Code/Old/06_census.R`, archived) assumed 4-digit codes (`"1000"`/`"3000"`/etc.), presumably written for an older/different PUMS vintage. Silently classified ~100% of rows as "hispanic" (the `fcase()` default).
  2. MIGSP is populated for every row, not just movers (contrary to the comment carried over from `acs_reweight.R`), and is zero-padded to 3 characters ("001"=Alabama) vs. ST's 2 ("01") — comparing them as strings made `MIGSP != ST` true almost universally. Fixed by comparing as integers, restricting to MIGSP ≤ 56 (valid US state/DC range; Puerto Rico=072 and foreign-country codes 100+ fall back to current state, same treatment as a non-mover).
  - `Code/acs_pull.R` now checkpoints the raw pull separately (`Data/intermediate/pums_raw_pull.rds`) from the derived columns specifically so a future fix to this derivation logic doesn't require re-hitting the Census API (51 states x 80 replicate weights, real wall-clock cost).
- **`P:\BRAIN_DRAIN\Data` is a network share** (`\\dataden\Project`, confirmed via `Get-PSDrive`/`Get-SmbConnection`), not local disk — loading `column1_covariates.rds` (4.2GB) or `column2_reweighted.rds` (1.15GB) genuinely takes ~11 minutes each, dominated by network I/O, not CPU. A process that looks "stuck" on one of these loads with slowly-climbing (not flat) memory in `Get-Process ... | Select WS` is healthy, just slow — don't assume a hang from this alone; check whether CPU/memory are still moving at all across a couple of checks first.
- **A `get_pums()` call can hang silently with zero error, forever** — no default HTTP timeout in `httr` (which tidycensus uses under the hood). Confirmed directly: one state's pull sat with completely flat CPU and memory for 20+ minutes with no exception raised, so a retry wrapper built only around `tryCatch` never fired. Any future script calling `get_pums()` in a loop should set `httr::set_config(httr::timeout(...))` up front, per `acs_pull_1yr.R`'s fix.
